# 鸡宝厨房：账号、存档、同步与玩家反馈方案

> 2026-10-08 更新：本文保留 10 月 7 日的审计与设计基线。用户后续确定本地自动保存＋手动云备份；相关代码已完成本机验证，尚未部署。当前实现、Cloudflare 测试目标、会话／历史简化、微信研究及待验项见 [实施报告](cloud-wechat-implementation.md)。下文 CloudBase 首选、自动同步与分层历史等是历史候选，不代表已经实施。

调研基准：2026-10-07。状态：**审计与设计，尚未实现云端功能，未开通或购买服务**。负责人文档：[工程与维护](../engineering.md)；界面落地后归入 [UI／美术](../ui-ux.md)，执行状态仍由 [当前计划](../plan.md) 管理。本附件在选型与验收完成后收束，只保留决策和可复核证据。

## 1. 决策与预算结论

建议保留当前本地事务存档，补齐历史备份与账号隔离，再接入独立的低频同步层。主技术方案选 **腾讯 CloudBase 上海地域、文档数据库与云函数**；备用技术方案选 **Cloudflare Workers + D1**，但必须先通过玩家真实大陆网络测试。两者都保存完整游戏 JSON，不把鸡宝、订单、寻访拆成在线服务器玩法。

这里有一个不能省略的限制：**本次没有核实到同时满足“大陆长期稳定、首次付款不超过 50 元、全年小于 50 元、无条件长期运行”的完整托管方案。** CloudBase 免费体验可以作为十人封闭验证环境，但不能承诺全年正式运营；其当前个人版优惠价 19.9 元/月，全年按现价算 238.8 元，超出预算。资源用量价值低于 50 元，不代表能按这个价格购买全年服务。[CloudBase 定价](https://cloudbase.cloud.tencent.com/pricing)、[资源点与体验规则](https://cloud.tencent.com/document/product/876/127357)

因此，“现在给十几个国内玩家用”的明确建议是：**先发布本地安全与导出能力；CloudBase 作为有期限、有独立备份的封闭云存档试运行。暂不把它宣传为永久云存档。** 若正式运营要求不依赖免费续期条件，当前预算下应暂缓云功能的正式承诺，不能把更贵方案悄悄纳入预算。备用 Cloudflare 也不是大陆稳定性的等价替代品。

新增的“设置 → 反馈与建议”纳入同一后端，提供离线草稿、提交回执、可选诊断信息；无需另买反馈 SaaS。保留 50 元预算，不预支域名、保证金或自动扣费。uniCloud 支付宝按量方案虽然用量便宜，但要求 200 元保证金，已经按用户“首次支付也不超过 50 元”的要求排除。[uniCloud 计费](https://doc.dcloud.net.cn/uniCloud/price.html#balance)

### 2.3 保存位置和平台行为

| 环境 | 实际位置／键 | 更新与丢失边界 |
|---|---|---|
| Android 正式游戏 | `Context.getFilesDir()/saves/{name}.json`，通常 `/data/user/0/com.jibao.kitchen/files/saves/`；`/data/data/...` 是常见别名 | 同包名、相同签名覆盖升级通常保留；不同 Android 用户有不同目录。卸载、清除应用数据会删除这里的当前档和备份 |
| Android WebView | 固定资源源站 `https://appassets.androidplatform.net/web/index.html`；游戏主档走原生桥 | 不是“WebView 的 localStorage 就是安卓主档”。UI／诊断仍可能用 Web Storage |
| Desktop / Web 正式入口 | 浏览器当前 profile 的 localStorage，主键 `chick-kitchen-v1` | 数据绑定 scheme + host + port 和浏览器 profile。localhost 与 127.0.0.1、不同端口、不同浏览器不能互读；隐私模式、站点数据清理会丢 |
| 评审／历史入口 | `chick-kitchen-review-v1`、`chick-kitchen-classic-review-v1`，历史 baseline 页面 | 是隔离进度，不随意自动合并到正式主档；不在当前 APK 正式模块集合里 |

浏览器底层物理数据库路径由浏览器和 profile 管理，没有一个跨 Chrome/Edge/系统固定的“鸡宝厨房 save.json”路径。Android `allowBackup=false`，所以不能假设卸载后 Android 系统云备份会替我们找回存档。

Debug 与 Release 当前 **applicationId 相同**，没有 debug 后缀；但 debug 默认签名与长期 release 签名不同。系统会拒绝不匹配签名的覆盖安装；若为解决安装失败先卸载，就会删掉应用私有数据。包名改变则分配另一套目录，旧数据可能仍在旧包下。版本号递增本身不意味着清档。

### 2.4 已有保护，不应重复开发

- `execute` 在隔离草稿上执行业务，推进确定性随机与逻辑时间，生成命令序号，再走统一 store；**持久化成功后才接受新状态**，失败保留旧状态。
- `createSaveStore` 已统一浏览器／Android 存取、严格校验、旧版本迁移、写失败锁定、并发外部修改检查、确认丢失后的回读判定。尚没有叫 LocalSaveManager 的总类，不等于没有统一边界。
- 浏览器有 `.previous`、导入前、升级前及 `.unreadable` 保护；多标签使用 `navigator.locks` 争取单写者，缺少该能力时按现有合同只读。
- Android 已使用 `AtomicFile`，保存带 magic、formatVersion、SHA-256 和原始 JSON 的 envelope；保留 previous、导入前、升级前备份。线程内同步避免交叉写；当前原始 JSON 上限 2 MiB，envelope 另有转义容量上限。
- SHA-256 按实际 UTF-8 原始字节校验；JS 与 Java 同时做结构、范围和业务交叉约束。当前损坏读取不是静默当新档覆盖；高版本档不认识时也拒绝降级写入。
- 正式经济写入经统一命令／保存接口。UI 偏好、诊断、系统提醒有单独存储，但不负责写 CP／伙伴库存。`HatchScheduler` 读取存档排提醒，不是另一套经济存档器。

### 2.5 当前触发频率

购买、收获、交付、解锁等业务提交直接保存；收获动画有短暂队列，暂停／输入重置会尝试刷出。100ms 游戏 tick **不等于每 100ms 写磁盘**：纯表现变化被过滤，逻辑时间有约 60 秒检查点，世界事件等实质变化会提交。启动、返回前台结算、pagehide、visibilitychange 和 Android pause 路径会尝试保存。

Android `onPause` 是向 JS 发异步消息再暂停 WebView；它不是系统保证“杀进程前 JavaScript 一定执行完”的机制。已确认的经济事务比“离开时再保存”可靠；尚未提交的收获动画、尚未落盘的非关键时间进度仍可能在强杀时回到上个检查点。

### 2.6 过去“更新后消失”的证据与结论强度

| 原因 | 当前证据 | 判断与验证方法 |
|---|---|---|
| 卸载后换签名安装 | 同包名 debug/release、不同默认签名；历史工程报告曾明确使用 debug APK | 有真实风险链，但不能据此断言某次事故就是此原因。取事故前后 APK 证书和安装记录确认 |
| 包名／Web origin／浏览器 profile 改变 | 原生私有目录和 Web 键的绑定方式明确 | 会表现为“新游戏”，可查旧包、旧 origin 的数据；不能把新入口空档直接写回旧档 |
| 清除应用或站点数据 | 存储确实位于可清理私有空间，allowBackup=false | 内部 previous 也救不了卸载；需外部导出或云副本 |
| 历史宽松读取 fallback | 历史／review `readSave` 有解析失败回 fresh 的路径 | 是历史风险，**不能套到当前严格正式加载路径**；没有事故档无法追认 |
| 更新结构不兼容 | 现有迁移与未来版本写锁可观察 | 当前已防御，但旧 APK、旧存档与崩溃记录缺失，无法完成事故级归因 |
| 崩溃、写满、坏文件 | 当前严格校验、previous、写失败回滚已有测试 | 不能由单元测试推出所有真机断电都安全；仍需故障注入 |

安全更新工具已在更新前备份、验证哈希，使用 `adb install -r --no-incremental`，安装后检查首次安装时间和存档哈希；不会主动 uninstall/clear。这条流程应继续保留。Git 可见历史不足以还原过去每次安装，报告不将推测写成已证实根因。

当前值得修的缺口：① previous 只有一代，快速正常写可能把“bug 前健康档”挤掉；② Android 正常从 previous 恢复后，再写 current 前没有统一将损坏 current 原字节隔离留证（浏览器已有此类保护）；③ 没有跨设备版本协议与账号本地分区；④ 没有云历史与独立供应商外备份；⑤ 当前启动保存可能制造无业务变化的本地 revision，不能直接据此每次上传。

## 4. 本地保存：先保住已经拿到的进度

### 4.1 频率与组件

保留 `execute → save-store → native/browser` 的已落地边界，用 LocalSaveManager 作为职责名称或薄封装即可。业务继续调用持久化命令，不重写成所有东西只 `markDirty()`。同步层只消费“已确认持久化的不可变快照”。

| 变化 | 本地规则 | 理由 |
|---|---|---|
| CP／材料消费、收获、抽取产出、奖励、交付、寻访回程、营业结算 | 立即提交，成功后才显示完成 | 已有事务保护不能为了统一 debounce 而退化 |
| 声音、页签等非经济偏好 | 约 3 秒合并，最长 30 秒落盘 | 可降低无关写入；失败不影响经济存档 |
| 逻辑时间推进 | 保留约 60 秒检查点；实际业务状态转换立即提交 | 不需要每帧持久化倒计时 |
| 后台、关闭、切号、导入、迁移、恢复 | 立即 flush；平台允许时读回确认 | 生命周期回调是补充，不是唯一保险 |

单份实测仅数十 KiB，暂时没有为经济数据延迟 5–10 秒保存的收益证据。以后若卡顿，再测低端 Android 写入 p95，并按“同一个批量命令”合并，不能显示已获得奖励却只存在内存。待存盘位另叫 `pendingLocalCommit`，不得复用游戏的 `state.dirty`。

### 4.2 原子写、校验与备份数量

Android 继续用 AtomicFile（临时／备份、完成写入及同步机制），不另写一套 rename 协议，也不为十人的整档存储引入 SQLite。AtomicFile 只保证单文件更新，不保证多文件一起事务：将“游戏 JSON＋账号归属＋同步基线”放进同一个版本化 envelope，备份先成功，再替换 current。旧原始游戏 schema 不与 envelope 版本混用。

浏览器目前单键写入能隔离单次替换，但多键备份／账号元数据不构成事务。新增多账号时采用 IndexedDB 同一事务保存 profile current、同步元数据和必要备份；老 localStorage 先复制、校验、读回，再切换入口，旧键留作迁移备份，不先删。申请持久存储只能降低浏览器回收概率，仍需要导出。

**每个本地 profile 正常保留 8 份：current、previous、3 份间隔至少 5 分钟的时间检查点、3 份保护快照。** 保护快照用于导入／迁移／冲突／恢复前，按明确顺序淘汰最旧已确认保护项；另留至多 2 份损坏原字节隔离件。未知未来版本档不参与自动淘汰，先要求外部导出再允许破坏性替换，避免无界累积。

按 64KiB 预算，8 份约 512KiB/profile；2MiB 极限则原始内容 16MiB，Android JSON 字符转义封装还会放大，实际磁盘预留必须按 envelope 大小计算。恢复时检查 magic／envelope 版本、长度、SHA-256、JSON、schema 与语义：例如负 CP、未知伙伴引用、重复交付、截断批次、库存预留超过库存都应拒绝。哈希一致只能说明字节没变，不能证明业务合法或未作弊。

先隔离损坏 current，再按 previous／时间检查点顺序验证。只在找到完整合法、兼容、同账号同谱系的档后恢复，明确提示“已恢复到××的本机备份”。全部失败则只读保护并允许导出诊断，不能用默认新档覆盖。没有文件的首次启动与“文件存在但读取失败”必须是两个状态。

### 4.3 迁移与旧客户端保护

现有 v1→2 增工具结构、v2→3 进度规范化、v3→4 事务／随机／时钟／扩展、v4→5 营业与事实／订单／库存、v5→6 收藏／常客／项目／菜单迁移可以复用。迁移在克隆对象上逐级运行、前后校验，不顺便结算离线时间，也不重新抽奖励。过去技能改版的一次性返还须保留完成标记。

每次结构／语义不兼容变更升 schema；兼容可选字段并非每次都要升，但旧校验器可能拒绝新状态，仍需可读／可写能力门槛。迁移前保存原字节，迁移成功持久化后再启动离线结算命令。内容版本用于解释 ID，不替代 schema。

云端记录 `schemaVersion`、`contentRevision`、`minReaderBuild`、`minWriterBuild`。例如云档 schema 7、旧客户端只支持 6：旧端只获取“需要更新”的头信息，不能下载后硬补默认值，更不能上传 schema 6 覆盖；旧端可以保留自己的本地离线分支，更新后再解冲突。服务端同时校验上传能力，不能只靠前端按钮隐藏。

## 5. 账号、云数据和安全边界

### 5.1 用户名密码模型

十个熟人玩家适合用户名＋密码、管理员重置。用户名建议 3–24 位 ASCII 字母／数字／下划线，统一小写唯一；显示昵称另设。密码 10–128 字符，允许粘贴，不要求手机或邮箱。服务端仅允许预登记的十个用户名注册，后台扩容白名单；玩家注册表单仍只有两个输入，避免开放注册被刷满额度。

CloudBase 文档支持用户名密码登录，但当前 v2 注册文档仍涉及 email/phone 验证；**“支持用户名登录”不能直接推论“支持完全无邮箱手机的自助注册”**。旧 username-login 文档也不能当新 Auth 的完整注册合同。本方案将小型认证服务放云函数中；如果后续实验证明官方管理端可安全创建纯用户名账号，可用同一界面替换实现，不伪造邮箱占位。[v2 Auth](https://docs.cloudbase.net/api-reference/webv2/authentication)、[旧用户名登录](https://docs.cloudbase.net/authentication/method/username-login)

使用成熟密码库，优先 Argon2id；受云函数运行时限制时用标准 `crypto.scrypt`，参数按 OWASP 当前建议选取并实测。不可把 SHA-256(password) 当密码散列；盐、参数与算法版本一起保存。免费函数 CPU／内存／超时不够时先判定部署方案不适用，不能削弱密码算法来适配额度。[OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

服务端生成随机 UID；短期访问会话约 15 分钟、刷新会话约 30 天，使用高熵随机 token，数据库只存 token 哈希，支持设备会话撤销与轮换。原生敏感会话由 Keystore 保护的存储保管；网页优先安全 HttpOnly Cookie（验证跨源 SameSite／CSRF），做不到时短 token 留内存，不能把管理员密钥放进 JS。Android 可通过仅受信离线页面可调用的窄桥代持凭证。

忘记密码通过管理员在既有熟人联系渠道核对身份，签发短时单次重置凭据；重置后撤销全部会话。不要只问“你的用户名是什么”就重置。此处是机制设计，本轮不发送任何消息或重置账号。

### 5.2 云端保存完整 JSON

选择文档库是为了复用 JSON、少表关联和原子条件提交，不是因为实时订阅。无需长连接，不需要把每只鸡建一行，不需要消息队列、Redis、排行榜或独立后台网站。

| 集合 | 内容与限制 |
|---|---|
| `users`／私有凭据 | UID、唯一规范用户名、密码参数与哈希、账号状态、创建时间；普通客户端无直接访问权限 |
| `sessions` | token 哈希、UID、设备、过期／撤销状态；限制每人活跃会话数，过期清理 |
| `current_saves` | 以 UID 固定文档 ID；完整原始 JSON、SHA-256、字节数、schema、内容版本、游戏版本、cloudRevision、cloudEpoch、saveId、设备、uploadId、服务端时间、展示摘要 |
| `save_snapshots` | 不可变旧档，同 UID＋独立快照 ID，来源版本、原因、保留类别、完整内容与哈希；禁止客户端直接删除 |
| `feedback` | 去重提交 ID、类别、正文、可选联系信息／诊断、UID 或匿名标识、回执与处理状态 |
| `releases` | 平台／渠道当前版本、兼容门槛、安装包信息、更新说明；公开只读，无玩家数据 |

游戏 JSON 作为原始字符串保存，防止服务端序列化改变哈希。外层字段负责同步和检索；服务器重算哈希及可信摘要，不信任客户端自报的 UID／版本摘要。默认请求上限建议先设 512KiB（规划常态 64KiB、压力 256KiB），超限返回可解释错误并保住本机档；当前本地 2MiB 合同保持不变，云端扩容前需验证服务单条和网关限制，不能先截断 JSON。

D1 单行／BLOB 上限 2,000,000 字节，不等于本地 2MiB＝2,097,152 字节，且整行还有元数据；Firebase 文档 1MiB、Bmob 旧限制 40KiB 也不能忽略。若未来整档接近云上限，单独设计对象存储＋事务指针，第一版不提前引入。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

### 5.3 历史保留和外部备份

每个账号 **current＋最多 20 份历史**：10 份近期、7 份每日代表、3 份迁移／导入／冲突／恢复前保护件，去重后可以少于 20。每日档最长 7 天；保护件按明确替换顺序，不许无界永久增长。冲突选中的两支都必须先保住；若保护空间不足，先导出最旧保护件，不能为了凑配额先删唯一健康版本。

上传事务先保留旧 current，再写新 current；恢复历史也写成一个**新的递增 cloudRevision**，不把云版本号倒回去。事务之外清理多余历史，清理失败只暂时多存，不能使 current 消失；清理只读不可变 ID，不删除并发事务正在保护的条目。

这 20 份仍在同一供应商，不能防整个环境被删。管理员另做加密离线导出，建议每日一次，保留 14 个日包＋4 个周包，至少两处持有。没有持续运行的管理设备时只能说“每次上线管理时补导出”，不能承诺每天自动成功；上线门槛需要落实执行人和成功记录。云端彻底不可访问后无法凭空导出，只能使用事故前的独立备份或玩家本机副本。

### 5.4 基础安全与费用防护

所有存档路径由服务端认证 UID 推导；请求体里传别人的 UID 不能换账号。数据库默认拒绝客户端直读直写，管理员密钥仅在服务端秘密配置。全程 HTTPS，禁止日志记录密码、token、完整存档和联系信息。限制 JSON 深度／大小，校验对象键和业务边界；错误向玩家给可理解文案，内部用去标识请求 ID 排查。

登录失败按账号与 IP 限速、递增冷却，避免永久锁死可被他人利用；注册只允许预登记用户名。同步按账号／设备限速，重试退避；对匿名反馈单独限额，不能让一条反馈接口耗尽存档预算。每人仅能列出／恢复自己的历史，管理员恢复记录原因并留最小审计。

用量在 50%／70%／85% 时分级提醒管理员；免费额度临近耗尽时延长自动同步间隔、暂停非必要诊断和版本轮询，必要时进入“云端暂不可用，本机已保存”。账单统计可能滞后，告警不等于费用硬上限；本预算下不开自动超额扣费。离线游戏不能保证防改档／改时钟，本轮安全目标是防越权和丢档，不是反作弊经济服务器。

## 6. 同步协议与账号隔离

### 6.1 必须区分的标识

- `profileId`：本机 guest 或 UID 命名空间；不同账号文件／IDB 记录隔离。
- `saveId`：一条存档谱系的随机 ID；不能靠最后修改时间判断谱系。
- `localGeneration`：每次本机持久化后递增；当前 `meta.revision` 仍保留现有业务合同。
- `baseCloudRevision`：当前本机分支所基于的云端版本。
- `cloudRevision`：服务器成功提交时递增的账号档版本，客户端不能指定新值。
- `cloudEpoch`：后端迁移／重建代际，避免把旧服务同号 revision 误认成新服务。
- `uploadId`：一份固定上传包的幂等 ID；重试不能偷偷更换内容。
- `sessionEpoch`：本机切换账号／退出时递增，旧网络回包不得写新账号界面或存档。

这些属于同步 envelope，不要求把游戏引擎变成联网引擎。

### 6.2 上传、下载与重试

**上传**：从已确认本地档捕获不可变 payload＋localGeneration，持久化待发送包和 uploadId。服务器鉴权、长度／schema／语义校验后，在同一事务中读取 UID 的 current：若 `expectedRevision` 不匹配，返回冲突；匹配才写旧档快照并更新 current、递增版本。创建首档同样以“记录不存在”为条件，不能先查询后无条件插入。

CloudBase 服务器端文档数据库提供事务；事务内按文档 ID 读取，不能把任意条件查询当成受保护读取。事务自动重试时必须重新校验客户端原 expectedRevision，不允许为了让重试成功而改成最新版本。[官方事务](https://docs.cloudbase.net/en/database/transaction)

相同 uploadId＋相同哈希若已存在 current／保留历史中，返回原提交回执并附当前 head；同 ID 不同内容拒绝。较早回执已被历史淘汰时，旧基线只能得到冲突，不能再次覆盖。确认回来后，只有捕获那一代仍是本机最新代且服务端 head 等于该回执时才能标“已同步”；上传期间产生的新进度继续 dirty。若新进度是该上传快照的连续后代，原子更新它的 baseCloudRevision 为已确认版本后继续上传；期间曾导入／恢复换谱系则不能套用这个基线。若 head 已前进则再检查分支，不把旧回执当最新。

**下载**：先看头信息和兼容门槛；在隔离对象中验证哈希、结构与游戏语义。只有“本地没有从基线发展、下载期间 localGeneration 未变、账号 sessionEpoch 未变”时才能自动应用。应用前备份，游戏内容和新的同步基线同一次本地事务提交，成功后再恢复计时与离线结算。已经发展的本机分支进入冲突。

**重试**：网络超时、5xx 用 5 秒、15 秒、60 秒、5 分钟上限的带抖动退避；恢复联网／手动同步可提前。401 转重新登录、409 转冲突、426 或 schema 不兼容转更新提示、413 转超限提示，不能统统无限重试。服务端未确认收到时不能显示已同步。没有网络可正常玩，只保留最新已落盘候选和一个固定在途包，不把每帧更新排成无穷队列。

可采用 HTTP `If-Match`／ETag 表达期望版本，但实际正确性来自**事务内的条件比较**；客户端时间戳只供人阅读。Steam Cloud 也需要处理跨设备分叉，并不意味着同步就是最后修改时间覆盖。[Steam Cloud 开发文档](https://partner.steamgames.com/doc/features/cloud)、[冲突帮助](https://help.steampowered.com/en/faqs/view/68d2-35ab-09a9-7678)

### 6.3 自动同步频率

默认有变化时每 **5 分钟**上传一次，进入／回前台查 head，联网恢复、手动同步、正常退出／后台时追加一次尽力提交。关键节点可安排 30 秒后的合并上传，但账号自动请求至少间隔 1 分钟，并受用量预算约束；高活跃玩家的额外上传成本按后文 1 分钟情形压力测试。纯声音／页签更改不触发云档上传。

回前台先给一次短暂同步检查机会（如约 2 秒），超时便使用本机进度并提示离线，不强迫等待云端；之后若查到另一设备分支则进入冲突，不自动替换正在玩的档。新设备没有本机档且断网时，可开独立游客档，但不能伪装成已载入账号档。

### 6.4 首次绑定、退出与切号

| 场景 | 必须行为 |
|---|---|
| 从未登录 | 独立 guest profile，可正常玩和导出 |
| 老玩家首次注册 | 先备份 guest；将完整内容复制并持久化到新 UID profile，服务端明确返回该 UID 无存档后，以不存在条件创建。guest 原件保留 |
| 云端返回空 | 只有成功鉴权的明确“不存在”才是空；超时、403、解析失败不能当空档，更不能覆盖本地 |
| 登录已有账号，本地 guest 有进度 | 先展示两个来源；明确选择绑定 guest 或载入云端，备份未选分支。不能仅因为刚登录便丢 guest |
| 新设备登录已有账号 | 完整下载、校验、落盘、读回后进入；失败时不建立同 UID 的伪新档 |
| A 离线玩 20 分钟后退出 | 先本地 flush 成功，最多短暂尝试同步；失败仍允许退出并提示“进度留在这台设备，尚未上传”，保留 A profile 的内容、基线和待传状态 |
| 本地保存失败时退出 | 不清会话／切档；保留当前内存并给重试、外部导出选择，避免把最后一份未保存内容销毁 |
| 退出后登录 B | 清 A 会话，切独立 B profile；A 的待上传包、反馈草稿、回包和提醒不能变成 B 的内容 |
| 再登录 A | 打开 A 原本地分支，再与云比较；不会把 B 或 guest 自动复制给 A |
| 两设备同账号 | 都可以离线玩；同基线分叉必须冲突，不强行踢下线，也不悄悄合并 |

退出不是删除本机存档。显式“删除此设备副本”单列并提示未同步状态；不要让普通退出按钮承担销毁数据的语义。

### 6.5 冲突与合并边界

A 完成地区寻访获得伙伴，B 同时收获 Farm 并买材料：二者都由同一云版本发展，应视为**整档分叉**。选 CP 大的一份会丢购买；库存相加会重复起始库存；图鉴集合并集可能满足奖励条件却没有对应交付／领取事实；寻访结算和营业预留又共享伙伴。因此 v1 不自动合并任何经济／进度字段。

音乐、音效、页面偏好可以按设备独立保存；这不是合并游戏进度。纯“看过提示”的集合未来可经证明后取并集，但应与奖励／引导解锁无关。当前声音仍在 schema 6 内，实施时先将旧偏好复制到设备层并适配旧字段，不可简单删掉导致旧校验失败。

冲突期间允许继续本机游玩但暂停自动上传；选择时重新捕获最新本机档和云 head，显示预览，避免拿十分钟前的冲突缓存替换后来进度。使用本机也必须 CAS 云 head 并保护云分支；使用云端先保护本机分支。若选择期间云又改变，重新显示差异。暂不处理不删除任何分支。

## 7. 同步状态机

| 状态 | 进入条件 | 主要转移与玩家文案 |
|---|---|---|
| SignedOut | 未登录／退出成功 | “进度保存在这台设备”；登录 → Checking |
| LocalReady | 本机已落盘，已确认与云同源且无待传 | 本地业务提交 → Dirty；回前台 → Checking |
| Dirty | 存在已落盘的新进度 | 定时／手动 → Uploading；断网 → Offline |
| Checking | 获取 head 与兼容信息 | 云无档 → 条件创建；本地清洁而云更新 → Downloading；双端发展 → Conflict |
| Uploading | 固定快照正在发送 | ACK 且代际无变化 → LocalReady；有新本地进度 → Dirty；409 → Conflict；超时 → Retry |
| Downloading / Applying | 隔离验证并落盘 | 本地未变且提交成功 → LocalReady；本地变了 → Conflict；损坏 → LocalError／保留原档 |
| Offline / Retry | 无网、超时、暂时 5xx | “本机已保存，联网后同步”；可继续玩，网络恢复 → Checking |
| Conflict | 两个有效分支 | “另一台设备也有新进度”；选择并保护两支 → CAS 提交／本地应用；稍后仍留 Conflict |
| AuthRequired | 会话过期／被撤销 | “请重新登录后同步”；本机仍可玩；认证成功 → Checking |
| UpgradeRequired | 服务端或存档格式不兼容 | “更新后可同步这份进度”；禁止覆盖，保留本地分支 |
| LocalError | 磁盘写失败／没有合法可用档 | 优先重试／恢复／导出；禁止宣布保存成功、禁止上传伪新档 |
| BudgetPaused | 环境到期／额度停服 | “云端暂不可用，本机进度保留”；保留待传、提供导出，恢复服务后 Checking |

任意网络状态遇切号都先终止 UI 关联并递增 sessionEpoch；迟到回包无权写新 profile。存档错误优先级高于网络错误，不能显示“网络不好”掩盖本地保存失败。

## 8. 丢档风险与灾难恢复

| 故障 | 防护与恢复 | 无法保证的边界 |
|---|---|---|
| 写入中断／半个 JSON | 原子替换／IDB 事务，SHA 与语义校验，previous 与时间检查点 | 硬件损坏可影响同盘多份，需外部副本 |
| current 损坏 | 先隔离原字节，再尝试同 profile 合法本地备份，提示恢复时间 | 不能将未知高版本误判为损坏后退档 |
| 全部本地副本坏 | 本地只读；登录后验证并恢复云 current／历史；保留坏件 | 未曾上传的进度云端不存在 |
| 云 current 错误覆盖 | 从受保护历史恢复为新 revision，先存当前分支 | 合法但错误的游戏逻辑不一定被哈希发现 |
| 云历史也坏／被删 | 免费 CloudBase 无付费回档保障，转供应商外加密导出；D1 备用可尝试 7 天 Time Travel | 不把同库 snapshot 当独立灾备；D1 库级恢复需另库验证后按 UID 导回，避免回滚其他玩家。[D1 恢复](https://developers.cloudflare.com/d1/reference/time-travel/) |
| 卸载／清应用数据 | 重装同签名后登录恢复；没有账号则导入外部文件 | 私有目录里的八份一起删除，离线未导出部分不可恢复 |
| 浏览器清站点／换 origin | 登录恢复或从旧 origin 导出；固定正式地址 | 浏览器持久存储不能抵抗用户主动清理 |
| 更新／迁移失败 | 同包同签名覆盖更新、迁移前备份、版本拒写、保留可导出的旧原件 | 回退 APK 不等于回退 schema；旧 APK 不可强读新档 |
| 上传 ACK 丢失 | 固定 uploadId 重试／查询回执，原基线 CAS | 不重发一个改过内容的同 ID 包 |
| 两设备同时提交 | 事务 CAS 只允许一支成功，另一支明确冲突 | 不自动判断“金币更多就更好” |
| 退出／切号回包迟到 | 独立 profile＋sessionEpoch＋UID 校验 | 普通页面变量切换不足以隔离持久化 |
| 供应商暂停／停服 | 本地继续；使用事故前独立导出迁移，保留原 ID／游戏格式 | 服务已彻底关闭时不能保证还能在线导出 |

恢复目标：已成功本地提交的关键业务不应因普通进程重启丢失；未提交的表现／时间检查点允许回到上一次落盘。联网自动云副本目标约 5 分钟，后台提交只是尽力；断网多久，云副本就可能落后多久。独立灾备只有在每日导出成功时才能谈约 24 小时数据损失窗口，不承诺理论上无法保证的零丢失。

迁移供应商时：导出游戏原字节＋manifest（UID、saveId、schema、revision、哈希、历史关系），新服务逐份验证；密码哈希仅在算法／权限可迁移时受控迁移，否则要求重置，绝不导出明文密码。短暂冻结旧云写入，游戏仍离线可玩；新云设新 cloudEpoch 和旧基线映射，旧客户端访问旧服务只读／升级提示。双写不是第一版迁移策略，以免两个后端都接受新分支。

## 9. 真实大小与容量、请求、费用测算

### 9.1 实测方法与结果

以当前引擎把 47 份 golden／本轮玩法 QA 存档规范化到 schema 6，再加一份固定种子新档，按紧凑 JSON UTF-8 测量，共 **48 个样本**。它们是仓库测试／自动游玩样本，**不是 10 名真实玩家统计**，不据此断言未来上限。

- 新档 2,210 字节；旧 golden 样本迁移后约 2.2–7.6KB。
- 本轮复杂玩法样本约 18–38KB；最大 **38,338 字节**，最大 gzip **8,711 字节**。
- 规划按 **64KiB/档**，压力按 **256KiB/档**，当前本地硬限制 2MiB。
- 默认先不压缩云存档：简单、易导出、易校验。未来压缩需限制解压后长度，防止压缩炸弹。

可复算证据：[测量与容量脚本](../../artifacts/cloud-save-research/measure.mjs)、[逐样本与全部场景数据](../../artifacts/cloud-save-research/measurements.json)、[完整容量表](../../artifacts/cloud-save-research/capacity-table.md)。脚本只读仓库 QA 存档，不读取设备玩家档。

| 每人历史份数（另加 current） | 10 人原始空间，64KiB/档 | 100 人原始空间 | 判断 |
|---:|---:|---:|---|
| 3 | 2.5MiB | 25MiB | 太容易被快速上传替换 |
| 5 | 3.75MiB | 37.5MiB | 可做极简起步，跨天恢复不足 |
| 10 | 6.875MiB | 68.75MiB | 基本够近期恢复 |
| **20** | **13.125MiB** | **131.25MiB** | 推荐，能同时留近期／每日／关键操作 |

计费估算再乘 2，为 envelope／索引／元数据预留，即 10 人 26.25MiB、100 人 262.5MiB；不代表数据库实际计量一定等于两倍。256KiB 压力档再乘 4，100 人可能超过部分免费库限制，因此需要体积监控而不是永久写死“免费够用”。

### 9.2 统一请求模型

每月 30 天；每人每日 F 次，每次 30 分钟；人数 N，间隔 I 分钟。假设整个游玩过程都有变化，包含退出上传，进入时保守计一次整档下载。单位 MiB=2²⁰ 字节，供应商 GB 单价换算按 10⁹ 字节计算；实际 GB 口径以账单为准。

```text
E = N × F × 30                         月游玩次数
U = E × (ceil(30 / I) + 1)             月上传次数（含退出）
Q = U + 3E                            HTTP/函数请求：上传、查头、下载、会话刷新
R = 2U + 4E                           DB 读预算
W = 3U + E                            DB 写预算：current、快照、淘汰、会话
Auth = E                              自有认证刷新估计；首次注册另加 N
上行 = 64KiB × U
下行 = 64KiB × E + 2KiB × Q
```

R/W 是明确假设的预算模型，事务冲突、历史选择、登录防刷、限速存储实现可能增加调用，不能当厂商精确计费器。函数平均先按 256MiB、0.2 秒，即 0.05GB·s/次；真实密码登录比普通请求重，应单独实测。首次注册及少量密码登录包含在预留里，频繁重登或攻击必须重新估算。

## 10. 设置界面、反馈和更新

沿用现有厨房设置弹层、按钮与留白，不另做现代后台仪表盘。设置增加少量分组行：

```text
账号与进度       小鸡同学    [管理]
本机保存         刚刚已保存
云端备份         3 分钟前    [立即同步]
恢复以前的进度               [查看]
导出 / 导入存档              [打开]
反馈与建议                   [打开]
检查更新         1.5.18      [检查]
```

未登录显示“进度保存在这台设备，登录后可备份和换设备”。离线分别显示本机和云端状态；存盘失败红色错误应覆盖“已同步”等旧提示。不要给玩家展示 revision、checksum、collection、CAS 等开发术语。

### 10.1 冲突和恢复界面

标题：“两台设备都有新的进度”。并排或上下两张同风格卡片，窄屏优先上下；字段按真实玩法显示：

- “这台设备”／“云端”，上次游玩时间（参考）与游戏版本。
- 厨房 Lv、CP、已发现伙伴 x/241、Farm 伙伴总数。
- 当前锅：进行中／待收获／已空；寻访地区、队员与进程；当期营业状态。
- 提示时间仅供参考，手机时钟可能不同；不要把 CPU 时间或服务端上传时间叫最后游玩时间。

按钮“使用这台设备的进度”“使用云端进度”“稍后决定”。选择后说明另一份将保留在恢复记录；真正保存快照失败则不执行覆盖。历史页列时间、原因与相同摘要，先预览再恢复，不允许点一行就直接替换。

### 10.2 玩家反馈入口

设置 → “反馈与建议”。类别：遇到问题／存档问题／玩法建议；正文 20–2000 字；联系方式可选，提示“方便联系时填写”。不要求为反馈先注册账号，也不向玩家承诺自动即时答复。

默认只提交正文、类别、游戏版本和提交 ID；“附上设备与诊断信息”由玩家明确勾选，可预览机型／系统、最近有限错误、保存与同步状态。去除 token、完整 URL 查询参数、路径里的个人信息。**不自动附整份存档、密码、账号会话或截图**。排查确需存档时提供玩家主动导出、另行确认附加的流程。

草稿在本机单独存储，最多 10 份；点提交生成固定 UUID，断网标“等待发送”，下次联网重试，收到服务器回执后才显示“已收到，编号××”。重复点击／超时重试不得生成重复反馈。登录用户建议每日最多 5 条、游客每设备每日 3 条，再加 IP 与全局预算保护；设备标识可能伪造，不能只靠客户端限速。

管理端第一版直接使用有权限保护的云控制台筛选反馈，状态“待看／处理中／已处理”，不另开发客服系统、不购买邮件通知。普通用户只能读自己的回执；匿名回执用高熵访问凭据，不能遍历编号读别人反馈。联系方式解决后尽早删，建议反馈保留 90 天、脱敏问题统计可更久；反馈日志与游戏历史有不同保留周期。切账号不挪用前账号的草稿和诊断。

### 10.3 检查更新与安装包托管

公开小型版本 JSON 与更新说明可放同一函数／HTTP 路由，客户端手动检查或一天最多一次后台缓存检查。字段至少含平台、渠道、versionName、versionCode、minReaderBuild、minWriterBuild、APK URL、字节数、SHA-256、发行签名证书指纹与更新说明。版本 metadata 应随发行流程生成，不能靠手工改 UI 文案。

当前 Android Manifest 没有 INTERNET 权限，MainActivity 对非离线资源请求返回拒绝结果；联网实施需要增加网络权限，并明确放行可信 HTTPS API、处理 CORS。不能为了开网络把 JS 原生桥暴露给任意网页；外部下载页走系统浏览器，只有受信离线主页面能使用保存／认证桥。

安装使用长期同一签名、同包名、递增 code 的覆盖更新；检查更新绝不引导“先卸载旧版”。现有安全更新与外部导出流程保留。

本次观察 1.5.18 APK 为 **107,488,761 字节，约 102.5MiB**：10 人每人下载一次约 1.075GB，100 人约 10.75GB。包下载比几十 KiB 存档更容易吃额度。国内对象存储／CDN 适合后续正规发包，但要单列流量、回源和存储费用，不能借云存档函数返回 APK。以 CloudBase 上海当前 CDN 0.21 元/GB、回源 0.15 元/GB 做粗算，10 人每周全量更新约 55.9GB/年，流量价值约 11.7–20.1 元，另有存储／请求且会与体验资源点竞争；不是无条件免付费托管承诺。[上海云存储计费](https://cloud.tencent.com/document/product/876/127357)

在十人验证阶段优先沿用现有熟人发包渠道或已有可访问文件空间，版本页只指向经核验的下载地址；如果当前没有这种渠道，正式下载托管仍属上线前待解决项。GitHub Releases、境外免费托管不能未经国内网络测试就成为唯一更新渠道。不买域名也能先验证默认 HTTPS 测试入口；CloudBase HTTP 正式使用需已备案自定义域名，不能把测试入口交付为长期下载服务。
